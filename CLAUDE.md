# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this project is

Khalid's personal portfolio site. The original was built from a GitHub template and personalized with ChatGPT web + limited coding knowledge, pre-dating AI coding agents — expect rough, non-idiomatic patterns in it, not deliberate design choices.

**We are rebuilding from scratch instead of patching the original.** Read [MEMORY.md](MEMORY.md) before doing anything — it has the decisions, the current build status per section, and exactly where to find matching content in the old codebase. This file (CLAUDE.md) is the *how to work here*; MEMORY.md is the *what's true right now*. Don't re-derive either from scratch each session.

## Repo layout

- **Repo root** (`src/`, `public/`, `package.json` at top level) — the **old** Create React App site. Read-only from here on: it's a content/reference source during the rebuild (bio copy, project descriptions, timeline entries, images, styling ideas), not something to keep fixing. Don't edit it except to extract content, and don't delete it yet — it stays until the new site fully replaces it.
- **`web/`** — the **new** site: Next.js (App Router, v16+), TypeScript, Tailwind CSS, `lucide-react` for icons. This is where all new work happens. It has its own `package.json`, run commands from inside `web/`.
  - The **shadcn CLI is initialized** (`web/components.json`, style `base-nova`, headless primitives via `@base-ui/react` not Radix, `iconLibrary: lucide`). `web/src/lib/utils.ts` exports `cn()` (now via the `cn` npm package, swapped in by shadcn init — same API as the clsx+tailwind-merge version it replaced, no consumer changes needed).
  - **Two registries are wired up in `components.json`**, both installed the same way (`npx shadcn@latest add <namespace>/<item>`), but with different auth needs:
    - **`@react-bits`** (`https://reactbits.dev/r/{name}.json`) — public, no auth. `npx shadcn@latest add @react-bits/<ComponentName>-TS-TW`. **Prefer the `-TS-TW` suffix** (TypeScript + Tailwind) to match this project's stack, not `-JS-CSS` (plain `.jsx`/`.css`, breaks the all-TS/all-Tailwind convention) — flag it if a component only ships `-JS-CSS`.
    - **`@21st`** (`https://21st.dev/r/{name}`) — configured and working via `npx shadcn@latest add @21st/<author>/<slug>` (verified with `--dry-run`; `API_KEY_21ST` is set in `web/.env.local`, gitignored). **But the user found the separate `@21st-dev/cli` package unreliable** (its own `add` command doesn't read `.env.local`, only real shell env vars — confusing, so avoid recommending it) **and has decided to paste 21st.dev components manually instead of installing via CLI at all.** Treat 21st.dev components as pasted code by default (same handling as react-bits' pasted-code path below), not as something to `shadcn add`. The registry stays configured in case that preference changes — don't remove it, just don't default to using it.
    - Use `--dry-run` first on either to see what files/deps an item would add before committing, and `--diff`/`--view` to inspect without writing.
  - Component placement convention:
    - `web/src/components/` (flat root) — raw components as landed by `shadcn add @react-bits/...` or pasted in from 21st.dev, kept close to their original form.
    - `web/src/components/ui/` — shadcn-native primitives (e.g. the `button.tsx` from init) and small generic reusable atoms.
    - `web/src/components/sections/` — the actual page sections wired into `page.tsx`: composes the raw components above with real ported content. Create `ui/`/`sections/` as needed rather than pre-scaffolding empty ones.
  - `web/CLAUDE.md` / `web/AGENTS.md` are auto-generated by the Next.js dev server (re-added by `next dev`) and warn that this Next.js version may differ from training data — check `node_modules/next/dist/docs/` inside `web/` before relying on remembered Next.js APIs. Leave those files alone; they're not ours to edit.

`main` is the live production branch (still serving the *old* GitHub Pages site) — never push directly to it or merge into it without the user explicitly asking. Work happens on a feature branch until the new site is ready to cut over.

## The main workflow: "use X component for Y section"

The user is collecting components from **reactbits.dev** and **21st.dev** for nearly every section, and will either (a) paste code directly, or (b) ask to pull one via the shadcn CLI (`npx shadcn@latest add @react-bits/<Name>-TS-TW`, run from inside `web/`), with an instruction like "use this for the hero" or "use this for Contact." Each time, that means:

1. **Get it in.** For a CLI pull: run `--dry-run` first to see what files/deps it brings in, confirm the `-TS-TW` variant is what's being added (flag it if only `-JS-CSS` exists), then add for real — it lands flat in `web/src/components/`. For pasted code: place it the same way, or straight into `web/src/components/ui/` if it's a generic primitive.
2. **Install what it needs.** For pasted code, check its imports against `web/package.json` — reactbits/21st.dev components commonly pull in `framer-motion` (or `motion`), `class-variance-authority`, `gsap`, etc. (this project's shadcn primitives are `@base-ui/react`, not Radix — a component assuming Radix may need adapting). Install only what's actually imported, don't pre-guess. Icons: prefer swapping to `lucide-react` for consistency unless the component's icon choice is load-bearing (e.g. a brand logo).
3. **Build the section.** Compose the raw component(s) into `web/src/components/sections/<Section>.tsx` and wire that into `web/src/app/page.tsx` (or the relevant layout) in the right position.
4. **Port real content**, don't leave placeholder/lorem-ipsum text. MEMORY.md's section tracker says exactly which old file has the matching real content (bio text, skills, timeline entries, project list, social links) — pull it via `codegraph_explore` or Read, don't retype from memory.
5. **Update the tracker** in MEMORY.md: mark the section done, note which component/source was used, and flag anything ported imperfectly (e.g. a data shape that needs the user's input, like real project links/screenshots).

If a request is ambiguous (which section, which of several pasted components, whether to replace or add alongside existing work), ask rather than guessing — these are one-shot placements the user will look at directly.

## Code intelligence: CodeGraph

`.codegraph/` is initialized at the repo root and covers the **old** site (`src/`). It has not been re-run against `web/` yet — do that (`codegraph sync` or re-`init`) once `web/` has enough real code in it to be worth indexing; until then, prefer plain Read for `web/` files and CodeGraph for pulling content/structure out of the old `src/`.

- MCP tool `codegraph_explore` (when available): one call returns verbatim source plus call paths — use it before grep/Read for anything in the old codebase, especially when hunting for content to port.
- Shell fallback: `codegraph explore "<symbol names or question>"`.

## Conventions

- No speculative abstractions, config options, or "future-proofing" — this is a small personal site.
- Delete replaced/dead code outright (don't comment it out "for reference" — git history already has it). The old repo root has ~280 lines of exactly this kind of dead code as a cautionary example.
- Treat any credential (the old site's EmailJS service ID/template ID/public key are hardcoded and already known-exposed — see MEMORY.md) as sensitive: never hardcode in the new site, use env vars, and flag any newly-found hardcoded secret to the user immediately rather than silently fixing it.
- No destructive or hard-to-reverse actions (deleting the old site/workflow, DNS/domain changes, key rotation, force-pushing) without explicit confirmation.
